▸ 01 · Prologue

What This System Is, and Why It Exists

The Multi-Agent Quote Advisor is a LangGraph application that takes a customer-profile JSON and produces a structured home-insurance quote. It is designed for California and Florida personal-lines homeowners — the two states where statutory-protection rules are the most consequential for rating, and where the domain naturally partitions into roles (statutes, eligibility, hazards, coverage, pricing, validation).

The system sits squarely at Level 3 automation: an autonomous reasoning loop, with agents that decide their own control flow and tool selection inside that loop. It is not a chatbot (single-turn intent matching) and not a deterministic workflow (hand-authored DAG of LLM-as-helper). The graph itself is deterministic; the agents inside it choose what to do.

Eight agents share one typed graph state, communicate strictly through that state, and call deterministic Pydantic-IO tools. The graph orchestrator is a separate layer the agents do not see. Every claim downstream agents make traces back to an evidence_id — the audit backbone the Follow-up Agent walks at follow-up time.

Three architectural commitments distinguish this from a generic LLM demo:

① Statutory Pre-LLM Gate

A pure-Python rules engine fires before any LLM sees the profile. CA Prop 103 drops credit_score; FL §626.9741 applies a 1.0× neutral when credit is null. Prohibited fields literally never reach agent context.

② Per-Agent LLM Modularity

Fourteen distinct LLM seats — one per agent and Council persona — resolve via llm_registry.get_llm(role). Defaults in YAML; per-role override via QA_LLM_<ROLE> env vars. Mix Anthropic + OpenAI freely.

③ Deterministic Confidence (+ LLM rationale paragraph)

The confidence_score number is still an 8-signal weighted aggregator computed in pure Python (DEC-0004 unchanged). It is never an LLM self-rating. Hard-cap at 0.5 if any statutory rule is violated. DEC-0012 then adds one cheap LLM call that writes a 2-3 sentence rationale_summary paragraph for the user — the LLM has zero ability to modify the number.

The graph is deterministic. The agents inside it choose what to do.

The five runs in this walkthrough exercise different paths through that architecture. Runs One and Two walk the full fourteen-node pipeline on California (Profile A) and Florida (Profile B, the marquee statutorily-null credit case). The other three exercise the conversational-follow-up branches on the prior demo-a thread: the Follow-up agent (Self-Ask + DecisionTrace walker), the Counterfactual agent (Reflexion + state-fork), and the same Counterfactual agent under a multi-axis Tree-of-Thoughts inner expansion.

Why six tiers, not three. Working / semantic / long-term is the standard memory taxonomy. And we split procedural out because static lookups (statute citations, multiplier tables, prompts) are first-class load-bearing artefacts you would never put in RAM or SQL.

▸ 03 · The Cast

Seven Cognitive Patterns, Eight Agents

The reasoning architecture is deliberately heterogeneous. Each agent's pattern was chosen for fit, not uniformity. Self-Ask doubles up — once for routing (Intent) and once for explanation (Follow-up) — because those are genuinely different decomposition surfaces (DEC-0007 documents the choice).

PATTERN · SELF-ASK
🔵 Intent Classifier & ❓ Follow-up Explanation

Decompose a question into atomic sub-questions, answer each, compose. Intent uses it for binary routing labels; Follow-up uses it for open-ended rationale composition.

PATTERN · TREE-OF-THOUGHTS
🌳 Eligibility Triage

Generate K candidate market routes; score each by viability against state/risk signals; prune dominated branches; pick the highest score. Used standalone here and as an inner expansion inside the Counterfactual.

PATTERN · REACT
🔁 Risk Assessment

Iterative Thought → Act → Observe. The agent decides which hazard probe to run next based on what it just learned. ReAct fits exploratory work; for non-exploratory chains the system uses ReWOO instead.

PATTERN · PLAN-AND-EXECUTE
📋 Coverage Recommendation

Single LLM call drafts a plan (floors → perils → limits → endorsements). Execution is mostly deterministic tool dispatch, with an optional LLM polish on rationale prose.

PATTERN · REWOO
⚡ Pricing

Reasoning WithOut Observation. Planner emits a DAG of multiplier-lookup tasks; workers fan out via LangGraph Send in parallel; solver composes the chain. Two LLM calls total.

PATTERN · CRITIC-REFINE
⚖️ Validator + 👥 4-Persona Council

Generator (upstream agents) is challenged by four critics (Conservative Underwriter, Customer Advocate, Actuarial Analyst, Compliance Officer). Compliance has VETO power. Round-1 parallel positions; Round-2 cross-exam; weighted vote.

PATTERN · REFLEXION (+ ToT)
🪞 Counterfactual

Trial → Reflect → Retry. State is forked, mutated, and re-run. Implausible deltas trigger verbal self-critique; reflexion memory persists across turns. Multi-axis questions add a Tree-of-Thoughts inner expansion.

▸ 04 · The Switchboard

Why We Have an Intent Classifier, In Simple Words

Before going into the four runs, one agent deserves its own chapter — because without it, every run after the first would cost five times more and run an order of magnitude slower. The Intent Classifier is small, cheap, and easy to overlook. It is also the load-bearing piece that makes conversational follow-ups affordable.

The problem it solves

The system can do three different things: quote a new home, explain an existing quote, or run a "what-if" scenario. But the user just types one message — they don't tell us which mode they want.

Without an Intent Classifier, every follow-up message would have to re-run the entire pipeline (statutory gate → eligibility → risk → coverage → pricing → council). That would be:

  • Slow — eight agents, dozens of LLM calls, maybe twenty-plus seconds per turn
  • Expensive — five-to-ten times the token cost of a single follow-up
  • Wrong — re-running pricing on the same profile would just produce the same answer; it wouldn't actually answer the user's question

So the Intent Classifier is the switchboard operator. It reads the user's message once and decides: which of the four lanes does this go down?

A worked example

User says: "Why am I paying so much for wind coverage?"

The Intent Classifier asks itself — Self-Ask pattern, that's why this agent uses it:

Q1: Is the user describing a brand-new home or asking about an existing answer?  →  existing answer
Q2: Are they asking us to change something?  →  no, just explain
Q3: Is this about insurance at all?  →  yes, wind coverage
Q4: Therefore the label is…  →  EXPLANATION

The graph then routes to the Follow-up agent instead of the full pipeline. Follow-up walks the existing DecisionTrace DAG (it's already in memory thanks to the MemorySaver SQLite checkpoint), pulls the top-three pricing drivers, and writes a two-paragraph answer.

~3 swall time · vs. ~25 s for re-run
5×cost saving · vs. re-running pipeline
7 / 8agents skipped on follow-ups

Why Self-Ask is the right pattern for this seat

Self-Ask = "decompose the question into sub-questions before answering." The classifier has to weigh several signals — is there a profile? does the message reference a prior answer? is it asking for a change versus an explanation? — and a single-shot prompt would conflate them. Self-Ask forces the model to write down its reasoning in order, which makes the routing more reliable and far more debuggable in LangSmith.

The same Self-Ask pattern is used twice in the system (Intent and Follow-up) — that's the intentional doubling documented in DEC-0007. It is not a copy-paste mistake. "Deciding what the user wants" and "answering by walking the trace" are both decomposition problems; both benefit from the same explicit Q-then-A structure.

The architectural payoff. Every dollar and every second saved on follow-up turns in ▸ 07–▸ 09 traces back to this one routing decision. The Intent Classifier is the smallest agent in the system and arguably the highest leverage one — kill it and the cost savings on follow-ups die with it.

The Self-Ask decomposition the prompt forces

Self-Ask is not a free-form chain — the prompt enumerates four binary sub-questions that must be answered in order. The LLM's rationale field captures which branch the model took, and is verifiable in the captured traces.

  1. Is the input a question about insurance at all? — no → out_of_scope
  2. Does the input reference a prior quote in this thread? — no → new_quote
  3. Is it asking 'why' or 'how' about the quote? — yes → explanation   (traces/03-followup-explain.verbose.log: "The input is asking 'why' about a previously-issued quote, indicating a desire for clarification on its cost.")
  4. Is it asking 'what if' or proposing a hypothetical change? — yes → counterfactual   (traces/04-followup-cf.verbose.log: "The input is asking about a hypothetical change regarding the removal of a pool.")

The prompt also instructs: "When uncertain, prefer counterfactual over explanation" — a deliberate bias toward the costlier-but-more-actionable branch when the question is ambiguous (the user probably wants the answer, not just the rationale).

Deep dive · the six questions

WHO
Influence & impact. — Every downstream agent. RiskAgent reads sanitized_profile (with credit dropped); CoverageAgent reads required_coverages + floors; PricingPlanner reads field_treatments to emit the right multiplier-lookup tasks; the Validator quotes statutory_violations as a hard check. A wrong field treatment compounds invisibly — credit not dropped means a $900K CA quote silently illegally penalises a 700-score customer.
WHAT
Hidden obstacle. — jurisdiction cross-contamination at retrieval. The CA and FL corpora carry near-identical statute prose; without the mandatory jurisdiction filter at retrieval (DEC-0003) the agent could cite §626.9741 (FL) for a CA customer. All six retrievals on this run carry jurisdiction=CA; you can verify by grepping the verbose log.
WHERE
Source & destination. Inputs come from the IntentClassifier's output. Retrievals hit ChromaDB at .chromadb/, corpus ca_doi (12 chunks indexed by make ingest). Outputs land in eight separate GraphState fields; sanitized_profile writes the credit-dropped profile that subsequent agents read.
WHEN
Trigger & transition. Fires when state["intent"] == "NEW_QUOTE". Transfers to EligibilityTriage once structured output validates AND the grounding self-check passes (every emitted evidence_id traces back to a chunk that was actually retrieved during the run). On grounding < 0.5 the deterministic safety net runs.
WHY
Status-quo challenge. Why ReAct + RAG over the legacy hardcoded engine? — statutes evolve faster than tables. ReAct lets the agent ground citations in fresh corpus content; the legacy engine was kept as the Phase-5 safety net (DEC-0011) so a bad LLM output never reaches the customer. The cost is one extra LLM-loop per quote; the benefit is statute updates without code edits.
HOW
Recovery. Three layers of discipline: schema-locked structured output (no dict[str, Any]); the Phase-4 self-check (drop any rule whose evidence_id wasn't retrieved during this run; if >50% drop, discard the whole emission); the Phase-5 fallback to statutory_rules_engine.evaluate(profile) with a [FALLBACK] audit node prepended to the DecisionTrace. On this run none of the safety nets fired — grounding was clean.

Deep dive · the six questions

WHO
Influence & impact. — The CoverageAgent's endorsement plan and the Validator's actuarial cohort check both read market_route. Plain-English deep dive · what each of the 4 markets actually is

Think of EligibilityTriage as the front-door bouncer at an insurance "mall". The mall has four different stores selling homeowners insurance, and each store has different rules about who they'll serve, what they sell, and how much they charge. The bouncer's only job is to look at the customer at the door and decide: "which store should this person walk into?"

The bouncer never quotes a price, never recommends a coverage, never decides if the customer is risky. It just picks the right store. Once that decision is made, every other agent (Risk, Coverage, Pricing, Validator) walks the customer through that specific store — using that store's prices, that store's product menu, and that store's rules. Pick the wrong store and everything downstream is wrong: the customer either gets declined, overcharged by 50%, or sold a policy that won't cover the claim they care about.

🏪 1 · ADMITTED — the main department store
Market
ADMITTED
Who runs it
Private insurance companies (State Farm, Allstate, Mercury, Travelers, Liberty Mutual, USAA, Farmers, AAA, Nationwide…) that have applied for and received a license from the state Department of Insurance.
Who it's for
"Normal" customers — homes that fit the carrier's underwriting appetite. Moderate risk, average-condition home, average claims history, average credit (where allowed).
Cost
Cheapest of all 4 tiers. Why? Because (a) competition is fierce, and (b) the state forces these carriers to justify every dollar of their rates with actuarial data.
Regulated?
HEAVILY. Rates must be filed with — and in many states approved by — the state DOI before being used. Filings can take 12-24 months. Forms (the policy contract itself) are also state-approved.

Plain-English deep dive. The word "admitted" means the carrier has been admitted (licensed) by the state. Three things this gives the customer that no other tier offers:

  1. Guaranty Fund protection. Every state has an insurance guaranty fund — basically a backstop pool funded by all admitted carriers. If your admitted carrier goes bankrupt, the guaranty fund pays your claim (up to a state-set cap, usually $300K-$500K). This is huge — it's why admitted is the default.
  2. State-approved policy forms. The contract language is reviewed by lawyers at the DOI. You know what you're getting because the contract is standardized.
  3. Rate justification. The carrier had to show actuarial math proving the rate isn't excessive or unfairly discriminatory.

Examples in our two demo states. California: State Farm General, Allstate, Mercury, Auto Club (AAA), Liberty Mutual, USAA, Travelers. Florida: State Farm Florida, Universal P&C, Heritage, Citizens-spinoffs like Slide. Why it's the cheapest: competition + rate review + standardized forms make this the efficient market. Most customers should land here.

When ADMITTED won't work. The carrier's underwriting rules say no. In CA, that's usually because the home is in a high wildfire zone (FHSZ "High" or "Very High") — most admitted carriers stopped writing those after 2017-2018 wildfire losses. In FL, it's usually because the home is in a high-hurricane coastal county or has wind-mitigation features that don't meet carrier minimums.

🏪 2 · FAIR_DIC — California's safety-net store + private add-on
Market
FAIR_DIC
Who runs it
Two things bundled together: (1) the California FAIR Plan — a non-profit "insurer of last resort" pool created by California in 1968, funded by every admitted carrier in the state proportional to their market share; (2) a private DIC ("Difference-in-Conditions") policy that wraps around the FAIR Plan to fill its huge coverage gaps.
Who it's for
CA homes that admitted carriers have refused — usually because the property sits in a "High" or "Very High" Fire Hazard Severity Zone (FHSZ) under CAL FIRE's mapping. After 2017-2018 wildfires, this means a LOT of CA homes — entire towns in Sonoma, Napa, Lake County, parts of LA County.
Cost
Higher than admitted. FAIR Plan basic alone is roughly 1.4-1.8× admitted-equivalent, AND you need the DIC wrap (another ~30-50%) to get usable coverage. Total: roughly 1.6-2.0× admitted.
Regulated?
FAIR Plan itself is heavily regulated — it's a creature of CA state law. The DIC wrap is on the surplus lines / non-admitted side and is more lightly regulated.

Plain-English deep dive. The CA FAIR Plan was created in 1968 after the Watts riots, when private carriers refused to insure homes in certain neighborhoods. The state said "if private carriers won't write these homes, we'll force them to collectively share the risk via a pool." All admitted carriers in CA must participate — they share the FAIR Plan's losses (and profits) proportional to their market share.

The catch: the FAIR Plan policy is a DP-1 dwelling fire policy. It's incredibly bare-bones:

  • ✅ Fire, lightning, internal explosion
  • ❌ Theft (not covered)
  • ❌ Water damage from burst pipes (not covered)
  • ❌ Personal liability (not covered)
  • ❌ Loss of use / additional living expenses (limited)
  • ❌ Personal property (limited or excluded)

So if your home gets robbed, or a pipe bursts, or someone slips on your porch and sues you — FAIR Plan does nothing. That's where DIC comes in. A "Difference-in-Conditions" policy is a private wrap-around sold by surplus-lines carriers (e.g., Lloyd's of London syndicates) that fills the FAIR Plan's gaps. Together, FAIR Plan + DIC roughly approximate what an admitted HO-3 policy would have covered — but at significantly higher cost and often with more exclusions.

Why this tier is so common in CA today: the 2024 California Sustainable Insurance Strategy was created precisely because so many homeowners were getting pushed into FAIR_DIC after admitted carriers fled wildfire zones. The state is trying to lure carriers back to admitted, but the migration is slow. As of 2026, FAIR Plan policy count is at historic highs.

When EligibilityTriage picks this: in CA + FHSZ ∈ {High, Very High} → score 0.85 → wins.

🏪 3 · CITIZENS — Florida's state-owned store
Market
CITIZENS
Who runs it
Citizens Property Insurance Corporation — Florida's state-run insurance company. Created by the FL Legislature in 2002 by merging two earlier last-resort programs (the JUA and FWUA). Owned by the state of Florida — not a non-profit pool like CA's FAIR Plan, but an actual state-owned corporation.
Who it's for
FL homes that admitted private carriers won't write — usually because the home is in a high-hurricane-exposure county (Miami-Dade, Monroe, Broward, Palm Beach, the Panhandle), or because admitted carriers in that ZIP code have hit their capacity limits.
Cost
CAPPED BY STATUTE — Citizens cannot charge more than the highest of the top 20 private carriers in a given territory (the "glide path" rule, Fla. Stat. §627.351). But this cap is being raised yearly because Citizens has been undercharging relative to actual hurricane risk; capped rate increases of ~14% per year per policy.
Regulated?
State-owned. The board is appointed by FL government officials. Heavily regulated by the FL Office of Insurance Regulation (OIR).

Plain-English deep dive. Citizens is fundamentally different from CA's FAIR Plan in three ways:

  1. It's a real insurance company, not just a risk-sharing pool. It has its own claims adjusters, its own staff, its own systems. Customers interact with Citizens directly, not through their normal admitted carrier.
  2. It sells real HO-3 policies, not bare DP-1. A Citizens policy actually covers liability, theft, water damage, loss of use — the same perils a private HO-3 would. Florida designed it this way because hurricane-displaced homeowners need real coverage, not a fire-only stub.
  3. Its rate is capped — but that's a problem. Because Citizens by law can't charge what its losses justify, every major hurricane season eats into reserves. After Hurricane Ian (2022) and Idalia (2023), the legislature has been steadily allowing larger annual rate increases to "depopulate" Citizens (move customers back to private carriers). Even so, Citizens currently has ~1.2 million policies in force as of late 2025.

Special FL-statute features baked into Citizens policies:

  • Hurricane deductible options under Fla. Stat. §627.701 — customer must be offered $500, 2%, 5%, or 10% of dwelling value as a hurricane-only deductible (separate from the regular all-other-perils deductible).
  • Mandatory CGCC (Catastrophic Ground Cover Collapse) under §627.706 — every Citizens policy must include this.
  • Optional sinkhole coverage under §627.706(2) — must be offered separately, customer can decline with a signed rejection.

When EligibilityTriage picks this: in FL + hurricane ∈ {High, Very High} → score 0.65 → usually wins (admitted scores 0.55 in that scenario, so Citizens edges it out).

🏪 4 · SURPLUS_LINES — the specialty store of last resort
Market
SURPLUS_LINES
Who runs it
Non-admitted carriers — companies that have NOT been licensed by the state DOI but are still allowed to write policies through specially-licensed surplus lines brokers. Examples: Lloyd's of London syndicates (the most famous), Lexington Insurance (an AIG subsidiary), Scottsdale Insurance (Nationwide subsidiary), Markel International, various specialty E&S writers.
Who it's for
Anyone the other three tiers reject. The "if all else fails" option. Common scenarios: multi-million-dollar coastal estates that exceed admitted carrier limits; homes with serious risk markers (multiple prior claims, historic property with non-standard wiring, exotic features like a private theater); homes in jurisdictions with no admitted appetite at all.
Cost
Most expensive — NO rate caps, no DOI rate review. Premium is whatever the underwriter writes on the binder. Typically 1.6-2.4× admitted-equivalent, sometimes much higher for unusual risks.
Regulated?
LIGHTLY. Two things customers should know: (1) NO state guaranty fund coverage — if the surplus lines carrier goes bankrupt, the customer eats the loss; (2) buyer pays a state-specific surplus lines tax (~3-5%) on top of premium.

Plain-English deep dive. "Surplus lines" sounds technical but the concept is simple: the state lets non-admitted carriers serve customers the admitted market refused, with fewer rules and no state safety net.

Why it exists: if surplus lines didn't exist, customers with unusual risks (a $20M waterfront mansion, a 19th-century historic home, a property with serious claims history) would be uninsurable. The state's bargain is "we'll let unregulated carriers serve you, but you give up consumer protections."

How a customer accesses it: they can't buy directly. They have to go through a surplus lines broker — a specially-licensed agent who has the authority to place business with non-admitted carriers. The broker submits the risk to multiple surplus lines markets (Lloyd's syndicates often want 3-week underwriting reviews) and brings back quotes.

The big consumer warnings the system must surface in warnings[]:

  1. "This quote is from a non-admitted carrier. The [state] guaranty fund does NOT cover claims if the carrier becomes insolvent."
  2. "Surplus lines premium is subject to a [state-specific %] surplus lines tax."
  3. "Policy forms are not state-approved; coverage terms vary widely by carrier."

Why EligibilityTriage rarely picks this: because it's the bottom of the barrel. The deterministic scorer gives it a flat 0.50 in CA and 0.45 in FL — high enough to "always survive pruning" (so it's a fallback if everything else fails), but low enough that it loses to ADMITTED, FAIR_DIC, or CITIZENS in normal scenarios. It only wins when the customer's profile is so unusual that the others are all hard-pruned or score below 0.50.

How EligibilityTriage picks the winner · step by step

Now that you know what each tier means, here's the actual decision logic in plain English. The agent always does the same 4 things, in order, no matter what the customer's profile looks like.

  1. Score every tier, even the impossible ones. The agent always considers all 4 tiers, even when one is obviously wrong. Why? Audit completeness. A customer or regulator might later ask "why didn't you put me with Citizens?" — the answer must exist in the trace, not be missing. So even for a CA customer, the Citizens branch is created and scored 0.00 with the rationale "Citizens is FL-only". That zero score and rationale get persisted in the DecisionTrace forever.
  2. Use two simple risk signals to score. The scorer needs to know — for CA customers: what's the wildfire zone? (fhsz_likely = Low / Moderate / High / Very High); for FL customers: what's the hurricane tier? (hurricane_tier = Low / Moderate / High / Very High). These two signals come from preview data the StatutoryAgent already collected. RiskAgent hasn't run yet — the agent works from rough hints, not full risk analysis.
  3. Apply the scoring tables (see the two tables below).
  4. Prune obvious losers, then pick the winner. Prune anything below 0.20 OR explicitly marked pruned=True (the Citizens-in-CA / FAIR_Plan-in-FL hard impossibilities). Then max(score) across the survivors. That's the chosen route.

Why this design beats a simple if/else

A tempting shortcut would be:

if state == "CA" and fhsz in {"High", "Very High"}: return "FAIR_DIC"
elif state == "FL" and hurricane in {"High", "Very High"}: return "CITIZENS"
else: return "ADMITTED"

This gives the same answer for our two demos, but it's worse in three ways:

  1. No audit trail. When the customer asks "why am I going to FAIR Plan instead of State Farm?", the if/else has nothing to show. The Tree-of-Thoughts version persists all 4 branches with scores and rationales — the customer can see exactly why each alternative lost.
  2. No statutory override hook. If the StatutoryAgent fires a route_market: 'fair_plan_check_if_fhsz_high' rule, the if/else ignores it. The ToT version's optional LLM polish pass reads market_route_hints and can override the deterministic pick if statute requires.
  3. No graceful gradient. The if/else only knows "winner / loser". The ToT version preserves how close the runner-up was — useful when downstream agents need to decide between explaining "clear winner" vs "close call between A and B" in the customer-facing explanation paragraph.
EligibilityTriage decides which of 4 insurance markets the customer should be placed in — Admitted (cheapest, mainstream), FAIR_DIC (CA wildfire safety net), Citizens (FL hurricane safety net), or Surplus Lines (last resort) — by scoring all 4 candidates with simple deterministic rules, pruning obviously-bad ones, and picking the highest survivor — then persists the full scoring trail so every downstream agent and any future audit can see why this market and not the others.

In simple words · what RiskAgent actually does

RiskAgent is a "hazard detective" — it figures out what natural and home-specific dangers threaten this property, calls real geographic-data tools to look them up, and produces a labelled list of risks (Wildfire, Hurricane, Flood, Earthquake, etc.) with a severity rating (low / medium / high) and a citation for each one.

Think of it like this: the customer says "I have a home at 33.42°N, -118.5°W with a swimming pool, no prior claims." The RiskAgent looks at that location on a map, queries 7 different hazard databases, and comes back with: "Wildfire — HIGH (FHSZ tier Very High). Earthquake — HIGH (PGA 0.62g near San Andreas). Flood — LOW (not in SFHA). Pool liability — MEDIUM." That list is the risk fingerprint every later agent (Coverage, Pricing, Validator) reasons about.

What pattern is it built on? · ReAct (Reason + Act)

ReAct is an LLM reasoning pattern from a 2023 Yao et al. paper. The agent runs a loop:

┌──────────────────────────────────────────────────────┐
│  Thought:  "This customer is in CA — wildfire is a   │
│             top concern. Let me check the FHSZ map." │
│      ↓                                               │

│      ↓                                               │
│  Thought:  "Confirmed wildfire risk. Now seismic..." │
│      ↓                                               │

│      ↓                                               │

The LLM decides which tool to call next based on what it has just learned — it is not a fixed pipeline. If the FHSZ tool returns "Low" (no wildfire concern), the agent might skip the dog-breed liability tool entirely and go straight to flood. Adaptive tool selection is the whole point of ReAct.

"You are the Risk Assessment agent operating in a ReAct loop. You have access to deterministic tools for hazard lookup. The 3 important rules in this prompt:

  1. Be selective. "Don't call seismic for inland Florida" — if a tool clearly doesn't apply, skip it. Saves cost and noise.
  2. 3-5 tool calls. Hard budget. Most homes only need 3-4 hazard checks; more than 5 is usually the agent over-thinking.
  3. Every factor must cite an evidence_id from a real tool call. No hallucinating "the home is in a wildfire zone" without a tool result to back it up. This is the grounding contract — same idea as the StatutoryAgent's self-check.

Severity guidance, mapped from concrete tool outputs (not LLM gut feel):

high   : tier=Very High or High; OR claims_history >= 2; OR in-SFHA flood zone
medium : tier=Moderate; OR has_pool; OR claims_history == 1
low    : tier=Low; OR no risk factor present

In simple words · what CoverageAgent actually does

The CoverageAgent decides exactly which insurance coverage lines to recommend (Dwelling, Personal Property, Liability, Earthquake, Hurricane, Flood, etc.), sets a specific dollar limit on each one, and writes a citation-backed rationale for every recommendation.

Think of it like a menu builder at a restaurant where the menu changes based on the diner. A vegetarian gets a different menu than a steak-lover. A celiac gets a different menu than a non-celiac. The CoverageAgent looks at the customer's profile + risk factors + statutory rules and builds the right menu of insurance products for that exact person — not too thin (gaps in protection), not too thick (paying for coverage they don't need).

What pattern is it built on? · Plan-and-Execute

Plan-and-Execute splits the work into two LLM brains, not one:

┌─────────────────────────────────────────────────────────┐
│                                                         │
│   1. PLANNER (LLM #1)                                   │
│      Thinks: "What 4 things must this customer's        │
│      coverage menu cover, and in what order?"           │
│      Outputs: ordered plan of steps                     │
│           ↓                                             │
│   2. EXECUTOR (deterministic Python + LLM #2)           │
│      Thinks: "OK, run each step. Call the right tool.   │
│      Collect results. Build the coverage list."         │
│      Outputs: list of RecommendedCoverage records       │
│                                                         │
└─────────────────────────────────────────────────────────┘

Why the two-brain split? Coverage decisions involve two very different skills:

  • Planning — high-level reasoning about what's needed (which category of coverage, in what order, why).
  • Execution — mechanical tool-calling and structured-output assembly.

If you put both in one LLM call, the model often does the easy part well and skips the hard part (or vice versa). Splitting them lets the planner focus on the what and the executor focus on the how — each gets simpler, more focused prompts.

In our codebase: the actual implementation is mostly deterministic Python that follows a 4-step plan, plus an optional LLM "polish pass" that adds richer rationale prose and validates the deterministic output. So even if the LLM fails entirely (coverage_agent.py:180-181: except Exception: plan_obj = None), the deterministic engine still produces a valid coverage list. The LLM polishes; it never gates.

What the Planner's brain (the prompt) says

"You are the Coverage Planner. — prompts.py:73-80

The four planning steps in plain English:

  1. "What's the floor?" — Mortgage lenders impose a minimum dwelling-coverage requirement (usually unpaid principal balance or rebuild cost, whichever is lower). Statute also imposes minimums (CA §2051.5 mandates 24-month loss-of-use; GSE B7-3-02 sets the Coverage A floor for mortgaged homes). The plan starts here because floors are non-negotiable — every later layer must be at or above them.
  2. "What perils threaten this home?" — Look at the risk_factors RiskAgent produced. Wildfire HIGH → need extended replacement cost. Hurricane HIGH → wind coverage at high limits. Flood in SFHA → NFIP flood (separate policy). Each peril maps to a coverage line.
  3. "Right-size the limits." — Coverage A is the dwelling rebuild cost: max(floor, replacement_cost, home_value). Coverage B (other structures) is typically 10% of A. Coverage C (personal property) is 50% of A. Coverage D (loss of use) is 24 months in CA, 12 elsewhere.
  4. "Add the endorsements the state requires." — State-specific add-ons that the StatutoryAgent flagged as required_offers. CA → CEA earthquake companion. FL → CGCC + hurricane deductible options + wind mitigation inspection.

What the Executor's brain (the prompt) says

"You are the Coverage Executor. You are given a plan with 4 ordered steps. — prompts.py:82-86

Three load-bearing constraints:

  1. Limits are strings, not numbers. The public output contract says so — and limits aren't always numeric ("15% of Coverage A", "24 months", "full Coverage A"). Forcing them to a string keeps the contract uniform.
  2. Never invent. If a tool fails twice, the agent records the failure in consistency_flags and moves on. It does NOT fabricate a coverage line to fill the gap.
  3. Always emit ISO codes for downstream agents — Coverage A → COV-A, CGCC endorsement → END-CGCC, hurricane deductible → END-HURR-DED, etc.

The Compliance Officer Council persona retains a downstream VETO power, but it is a backstop — the gate is the first line.

▸ 09 · Run Five

Two Mutations, One Tree-of-Thoughts

The fifth run asks two questions at once: "What if I removed the pool and dropped credit to 600?" The Intent Classifier must extract two mutation axes from the natural-language sentence; the Counterfactual Agent forks the prior demo-a GraphState, applies both mutations, and re-runs Risk → Coverage → Pricing on the fork. Tree-of-Thoughts is the inner expansion that decides ordering when two mutations could interact.

The pool mutation drives the entire −10.7% delta — exactly the same delta as the single-axis run in ▸ 08. The architecture surfaces this honestly: the state_diff tool reports two mutated fields but the pricing chain only changed in one dimension. That is the system working, not failing.

The schema fix that made this work

Earlier in this work, this exact run failed with an OpenAI BadRequestError: "Invalid schema for response_format 'IntentResult': In context=('properties', 'new_value'), schema must have a 'type' key." OpenAI's strict structured-output mode requires every JSON-Schema field to have an explicit type; Any doesn't generate one. The fix was a one-line change to src/quote_advisor/schemas.py:

# Before
class MutationAxis(BaseModel):
    field: str
    new_value: Any   # ❌ no JSON-Schema type

# After
class MutationAxis(BaseModel):
    field: str
    new_value: str | bool | int | float | None = None   # ✅ typed union

With the typed union, OpenAI's strict mode accepts the schema and the Intent Classifier returns both mutation axes correctly. The actual 05-followup-cf-multi.verbose.log shows:

The marquee teaching moment. Compare the single-axis trace (▸ 08) with this multi-axis trace:

The credit_score: 600 mutation passed through the IntentClassifier (the typed-union schema fix handles it), passed through the Counterfactual fork (the deep-copied state has credit_score=600), but the StatutoryAgent re-ran on the fork and the CA-PROP103-CREDIT rule fired again — dropping credit_score from the sanitized profile before the Pricing chain ever sees it. The Pricing solver therefore emits the same MULT-CREDIT-DROPPED-CA-PROP103 → 1.0× entry in both runs.

This is exactly the architectural commitment: statutory protection cannot be bypassed via a counterfactual. The customer can mutate any field they like; the gate fires every time.

The Tree-of-Thoughts inner expansion

Once the two mutations are extracted, the Counterfactual Agent generates candidate orderings — pool-first vs. credit-first — and scores each. In this case the two mutations commute (pool affects only the liability/pool dimensions; credit is dropped by the gate before it can affect anything), so both orderings score the same. The agent collapses to one branch.

What this run reveals about the architecture. The credit_score mutation propagated through the Intent Classifier (typed-union schema accepts it), through the Counterfactual fork (deep-copied state carries it), and into the StatutoryAgent fork — where the CA-PROP103-CREDIT rule fired again and dropped it. By the time Pricing ran on the fork, sanitized_profile.credit_score was None just as in the base run. The pricing chain therefore stayed identical except for the pool dimension. This is the point of the gate: statutory protection is not a customer-facing veto, it is structural. A mutation cannot bypass it because the agent re-runs on every fork.

▸ 14 · Lessons

What These Five Runs Revealed

Documenting five runs at this level of detail surfaces things you cannot see from a passing test or a single demo. Some are architectural confirmations; some are bugs noticed and patched while the work was running; some are structural limitations surfaced honestly rather than hidden.

Confirmations

  • The StatutoryAgent (DEC-0011) works exactly as designed on both jurisdictions. Profile A's CA flow fired six rules from the ca_doi corpus across six RAG retrievals, dropped credit_score per Prop 103, and routed to fair_dic (high FHSZ tier in California). Profile B's FL flow fired five rules from the fl_dfs corpus across five retrievals, set field_treatment = neutral_fl_626_9741, and routed to citizens. Grounding self-check dropped zero rules on either run. Determinism is preserved by the Phase-5 safety net.
  • Statutory protection survives counterfactuals. The cf-multi run set credit_score=600 as a mutation; the same delta as the single-axis pool removal returned (−10.7%). The CA-PROP103-CREDIT rule re-fires on every fork — the credit field is dropped before the Pricing chain ever sees it. This is the gate working: a customer cannot bypass statutory protection by phrasing it as "what if".
  • Self-Ask doubles up cleanly. Intent (routing-binary decomposition) and Follow-up (rationale-open-ended decomposition) use the same pattern with different surfaces. DEC-0007 holds up.
  • Per-agent LLM modularity confirmed. gpt-4o-mini for routing/classification (INTENT_CLASSIFIER, ELIGIBILITY_TRIAGE, COVERAGE_EXECUTOR, FOLLOWUP_EXPLAIN, CONFIDENCE_EXPLAINER); gpt-4o for tool-using ReAct, planning, and complex structured output (everything else). The mix lands at <$0.025 per fresh quote. The exact map is verifiable by running with --llm-trace.
  • Synthetic-fallback caches kept demos working through real network failures. hazards.fema.gov blocks TLS handshakes from this environment; the fetcher's all-paths-failed branch returned a curated snapshot anchored on real publicly-disclosed FIRM panel IDs (06037C1620G, 12086C0312L, etc.), and the runtime tools never noticed the difference.

Bugs surfaced and fixed in this work

  • FIXED Pricing solver overrode deterministic numbers. The Solver's structured-output schema included point_estimate_usd / range_low_usd / range_high_usd fields, and gpt-4o helpfully recomputed them. Result: a single demo-a run that produced $50K-$83K instead of $4.7K-$8K. Fix: the solver now keeps point, low, and high as deterministic Python computations and only adopts the LLM's prose for the rationale. (See pricing_solver_node in src/quote_advisor/agents/pricing_agent.py.)
  • FIXED Pricing results compounded across re-runs on the same thread. The pricing_results field uses an operator.add reducer so parallel ReWOO workers can fan-in. But re-invoking the graph on the same thread_id caused MemorySaver to restore the prior list and the workers' new emissions concatenated to it — every multiplier got squared, cubed, etc. The result was a $2.8M premium on the third re-run. Fix: the solver dedupes by step_id keeping the latest occurrence.
  • FIXED OpenAI strict mode rejected the IntentResult schema. MutationAxis.new_value: Any doesn't generate a JSON-Schema type, and OpenAI's structured-output strict mode requires every field to have one. Fix: replace Any with the typed union str | bool | int | float | None. This unblocked all three follow-up demos.
  • FIXED LangSmith 401 spam cascaded into Risk Agent. A rejected LangSmith key caused the multipart ingest to fail repeatedly; on some langchain versions, that was enough to break the create_react_agent chain so the Risk Agent fell back to its deterministic factor list. Fix: configuration._bootstrap_langsmith now probes the key against an auth-required endpoint at startup and gracefully disables tracing if the probe returns 401, rather than letting the rejection cascade into runtime.
  • FIXED Circular import in agents/__init__.py. The DEFAULT_LATLON constant was defined after the agent imports in the package init; risk_agent.py's from . import DEFAULT_LATLON hit it during the partial-import phase and crashed. Fix: moved DEFAULT_LATLON to a new agents/_constants.py module that does not trigger the package init.

Limitations surfaced honestly

  • PHASE-2 Pricing factor names truncate to (? (?)) when they don't match the planner's keyword scan. The Risk Agent emits RiskFactor.factor as natural-language strings ("Wildfire", "Earthquake", "Overall Hazard", "General Hazard"); the Pricing planner's keyword map looks for substrings like wildfire, seismic, hurricane, flood. When the LLM picks a synonym (Earthquake vs. Seismic, General Hazard vs. NRI), the planner emits a multiplier-lookup task whose dimension defaults to 1.0×. Premium estimates are conservative-low until the keyword canonicalisation is improved (or replaced with a small classifier).
  • PHASE-2 Counterfactual mutations have no schema-level effect for fields the gate drops. Surfaced by the cf-multi trace (credit_score: 600 → no pricing change). This is correct behaviour at the architectural level — the gate fires on every fork — but a future refinement would explicitly explain to the user why their mutation produced no change ("Your proposed change to credit was nullified by Cal. Ins. Code §1861.10 (Prop 103) which prohibits credit-based rating in California; the pool removal accounts for the entire delta"). The DecisionTrace already carries the evidence; the Follow-up agent could compose this rationale.
  • PHASE-2 The Follow-up agent's RAG keyword router is brittle. "Why is this quote expensive?" matched none of the topic keywords, so RAG retrieval was skipped and the answer came purely from the DecisionTrace top-3 drivers (verified by traces/03-followup-explain.verbose.log: FollowupExplain · corpus=none · chunks=0). For richer follow-ups ("explain my CGCC", "how does FAIR Plan work in CA"), broadening the router or replacing it with semantic similarity over corpus titles would help.
  • PHASE-2 Confidence breakdown drifts on counterfactual reruns even though the overall stays at 0.95. Across base → cf-single → cf-multi, the per-dimension scores degrade: risk 1.0 → 0.9 → 0.833 and grounding 1.0 → 0.8 → 0.667. The hard-floor clamp at 0.95 means the customer-facing number is unchanged, but a discerning auditor reading the breakdown would notice the slip. A future refinement would surface "this counterfactual is less grounded than the base" in the rationale paragraph.
The architecture is sound. The bugs were in the joints — types, reducers, side-effect cascades — exactly where they should be.

▸ 16 · Recent Changes (DEC-0011 + DEC-0012)

Replacing the Hardcoded Engine With Two LLM Agents

Two architectural commitments documented in the earlier chapters were intentionally replaced after this walkthrough was first written. The product owner asked: can the hardcoded statutory rules and the deterministic confidence aggregator be re-expressed as LLM agents that read documents instead? The answer turned out to be different for each.

DEC-0011 — Statutory rules: full replacement (LLM agent in the gate position)

The pure-Python statutory_rules_engine.py that ran before any LLM saw the profile is now superseded by a five-phase StatutoryAgent at the same graph position. The agent uses ReAct over rag_retrieve to find applicable statutes in the seven jurisdiction-tagged corpora, including a new gse_lender corpus and four newly-authored chunks for previously-uncovered rules. Determinism is preserved by three layers of discipline:

  • Phase 3 schema-locked emission via with_structured_output — concrete-typed schema (no dict[str, Any]) so OpenAI strict mode rejects malformed output
  • Phase 4 self-check — every emitted evidence_id must trace to a chunk that was actually retrieved during the run; rules failing this check are dropped, and if more than 50% drop the entire emission is discarded
  • Phase 5 deterministic safety net — on any LLM error or low-grounding output, the legacy engine fires and a [FALLBACK] audit node is appended to the DecisionTrace

Downstream agents see no change — the agent emits the identical 8-field StatutoryEngineOutput that the engine produced before. Profile A still drops credit_score per Prop 103; Profile B still gets field_treatments[credit_score] = neutral_1.0x per Fla. Stat. §626.9741. The engine that DEC-0005 documented is now the safety net beneath the agent rather than the runtime path.

What changed under the hood for Profile B. Five real RAG retrievals fired during the run: fl_dfs / "credit-neutral §626.9741" → FLDFS-CREDIT-01; fl_dfs / "hurricane deductible §627.701" → FLDFS-HURR-DED-01; fl_dfs / "CGCC §627.706" → FLDFS-CGCC-01; fl_dfs / "sinkhole §627.706(2)" → FLDFS-CGCC-01; fl_dfs / "wind mitigation OIR-B1-1802" → FLDFS-WIND-MIT-01. Self-check dropped zero rules. The premium range came in identical to the deterministic baseline ($5,850–$9,750).

DEC-0012 — Confidence: deliberate non-replacement (LLM augments, doesn't replace)

The deterministic 8-signal aggregator was a different question. Every signal it computes is already an observable count or boolean — converting integers and counts into 0-1 scores is arithmetic, not reasoning. Wrapping that in an LLM would have spent cost and added regression surface to perturb a deterministic answer by ±0.05.

So DEC-0004 stays exactly as it was. The number, the per-dimension scores, the hard cap at 0.5 if statutory non-compliance, and the [0.05, 0.95] clamp all remain pure Python. DEC-0012 adds one cheap LLM call after the math runs, whose only job is to write a 2-3 sentence rationale_summary paragraph for the user. The LLM has zero ability to modify any number — it only writes prose. The system prompt forbids restating numbers and forbids contradicting the breakdown. On any failure the paragraph is None and the pipeline ships the deterministic number unchanged.

The shape of an honest replacement. The two replacements look symmetric on the surface but answer the question differently. The statutory replacement is full because the upside (statute updates without code edits) is real. The confidence replacement is narrow because the upside (a paragraph instead of a bare number) doesn't require an LLM in charge of arithmetic. Both designs end up where the LLM adds genuine value and stay deterministic where determinism matters.

Verification

A new tests/verify_replacements.py script runs four golden checks against the two demo profiles:

  1. Profile A — agent's triggered_rules, field_treatments, required_coverages, and sanitized_profile.credit_score all match the legacy engine's output exactly
  2. Profile B — same checks, including credit_score: neutral_1.0x
  3. Confidence explainer — produces a non-empty 200-400 char paragraph
  4. Hard-cap regression — synthetic statutorily-violating profile still scores ≤ 0.5

All four pass. Running the full demos end-to-end (make demo-a / make demo-b) produces premium ranges identical to the pre-change baseline ($4,790–$7,984 for CA; $5,850–$9,750 for FL), with the same statutory rules cited in the explanation. The new --verbose output surfaces the StatutoryAgent's full ReAct trajectory (corpus, jurisdiction, query, chunks retrieved, evidence_ids) and the rationale paragraph as a dedicated section.
